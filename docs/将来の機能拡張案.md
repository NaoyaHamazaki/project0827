# 将来の機能拡張案（Pythonで実現できるもの）

作成: 2026-11-12
位置づけ: 現時点では未実装。PoC の説明や、有料PoCの範囲を決めるときの材料として残しておく。
関連: [現在の仕様と開発状況.md](現在の仕様と開発状況.md)

受付システムで集まるデータ（入退室ログ、会議室予約、注文、間取り図、チャット）を使って、Python（Django 側）で追加できる機能の候補をまとめる。
すでに実装した3D表示（間取りの3Dビュー）以外のもの。

---

## 1. 機能候補の一覧

| # | 機能 | 概要 | 主なライブラリ・技術 | 使うデータ |
|---|---|---|---|---|
| 1 | 混雑ヒートマップ・混雑予測 | 曜日×時間帯の在室人数をヒートマップで表示し、先の混雑を予測する | pandas、scikit-learn など | 入退室ログ |
| 2 | 図面画像から間取りを自動作成 | 間取り図のPDFや写真から壁や部屋の輪郭を検出し、間取りエディタの図形に変換する | OpenCV | 図面画像 |
| 3 | 月次利用レポートのPDF作成 | 代表向けに、所属メンバーの利用時間・会議室の利用・注文をまとめたPDFを作る | WeasyPrint、reportlab | 入退室ログ、予約、注文 |
| 4 | 会議室の空き提案 | 人数・時間・日付の条件から、空いている部屋と時間の候補を出す | 単純な検索で可。複数の予約をまとめて最適に割り当てるなら OR-Tools | 会議室、予約 |
| 5 | 注文の需要予測 | 時間帯や曜日ごとのドリンク等の注文量を予測し、補充のタイミングを提案する | pandas、scikit-learn など | 注文 |
| 6 | AI受付チャット | よくある質問への自動回答。将来的には予約や注文の代行も行う | Anthropic SDK（Claude API） | 受付設定、お知らせ、予約、注文 |

### 優先度の考え方

- 説明動画やデモで価値が伝わりやすいのは **1（混雑ヒートマップ）** と **2（図面から自動作図）**。
  - 1 は、デモ用のログデータを作れば、数日分の画面をすぐに用意できる。
  - 2 は、既存の間取りエディタ・3D表示とつながるので、「図面を入れるだけで3Dまで見られる」流れを見せられる。
- **6（AI受付チャット）** は、既存のチャット画面とデータがそのまま使えるため、比較的手軽に形にできる。

## 2. 無料（説明動画）と有料PoCの分け方

精度や実データが絡む部分は、有料PoCで取り組む範囲とする。説明動画には「画面の形（ガワ）」だけを入れる。

| 機能 | 説明動画（今の無料の範囲） | 有料PoCで行うこと |
|---|---|---|
| 混雑ヒートマップ・予測 | デモ用の入退室データでヒートマップ画面だけ見せる（1〜2日で作れる） | 実際のログを集めて、予測の精度を検証する |
| 図面からの自動作図 | 「画像をアップロード → 図形が並ぶ」流れを、決まったサンプル図面だけで見せる | さまざまな図面に対応し、読み取りの精度を上げる |
| 利用レポートPDF | 1か月分の見本PDFを見せる | 実データでの集計と、出力内容のすり合わせ |
| AI受付チャット | よくある質問への回答を実際に動かして見せる（下記 3章の①） | 予約・注文の代行（下記 3章の②）、誤った予約の防止、運用ルールの整備 |
| 会議室の空き提案・需要予測 | 画面イメージだけ見せる | 実データでの検証 |

動画で「こういうことができる」という絵を先に見せておくと、有料PoCの範囲や費用を説明しやすくなる。

## 3. AI受付チャットの詳細

### 3-1. 作り方

- 今のチャット画面に「AI受付」という相手を1つ追加し、Django 側から Claude の API を呼ぶ（Python 用の公式SDK `anthropic` を使う）。
- 次の2段階で進める。

| 段階 | できること | 中身 |
|---|---|---|
| ① FAQ回答 | 営業時間・Wi-Fi・設備・ルールなどの質問に答える | 受付設定やお知らせの内容をAIに渡して答えさせる。1日程度で作れる見込み |
| ② 操作の代行 | 「明日10時から4人で会議室」→ 空き部屋の候補を出して予約、「コーヒー2つ」→ 注文 | 既存の会議室予約・注文の処理をAIから呼べるようにする（ツール連携）。実際に登録する前に、画面で「この内容で予約しますか？」と確認を挟む |

### 3-2. 押さえておく点

- **答えられない質問は人に渡す**：わからないときは管理者とのチャットに切り替える。既存のチャット機能を使う。
- **費用**：API 利用料が会話ごとにかかる。PoC 規模なら小さい額だが、有料PoCの見積もりに含める。
- **APIキーの管理**：Railway の環境変数に置き、コードには書かない。
- **記録**：AI の回答をログに残し、PoC の評価材料にする。
- **個人情報**：会員情報をAIに渡す範囲を決めておく（[チャット設定_AIマスキング仕様案.md](チャット設定_AIマスキング仕様案.md) と合わせて検討する）。

### 3-3. 着手に必要なもの

- Anthropic の API キー
- AI に答えさせる情報の整理（営業時間、Wi-Fi、設備、利用ルールなど）

## 4. 実装時の共通の注意

- **Railway の Serverless（無アクセス時スリープ）との相性**：予測の再計算やレポート作成を定期実行する場合、常駐処理（Celery、cron）はスリープと相性が悪い。管理画面のボタンや管理コマンドで実行する形から始める。
- **重い処理はリクエストと分ける**：図面の解析やPDF作成は時間がかかるので、処理中の状態を画面に表示し、終わったら結果を見られる形にする。
- **所管ごとのデータの範囲**：集計や予測は所管（拠点）単位で行い、管理者には自分の所管の分だけを見せる（会員管理と同じ考え方）。
