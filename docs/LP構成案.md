## 1. 前提

| 項目 | 内容 |
|---|---|
| 主な読み手 | 中小規模のコワーキングスペース・シェアオフィス・レンタルオフィスの**運営会社**（現場の責任者と、決裁する経営者） |
| ゴール | 有料PoC（実証実験）への申し込み |
| 打ち出し方 | 実績がまだないため、「PoC参加企業を募集中」「先着◯社」の募集型にする |
| 立ち位置 | オフィス向けの受付・会議室システムは「働く人（入居企業・社員）」のためのもの。このシステムは「**場をつくる人（運営者）**」のためのもの、と打ち出す。他社名は出さない |

## 2. キャッチコピー（2026-11-24 決定）

- **メイン**: 「場をつくる人のための、受付・会員管理システム。」
- **サブ（案）**: 「入退室も、カードの貸出も、会議室予約も、ドリンク注文も。運営の毎日を、ひとつに。」
- **ビジョンの一文（2026-11-24 決定）**: 「スペース運営の Workspace OS を目指して」

検討した他の案（不採用）:
- 「受付の“手間”を、仕組みで減らす。」（分かりやすさ重視。提案資料の表紙で使用中）
- 「入退室も、カードも、予約も、注文も。運営の毎日を、ひとつに。」（機能の広さ重視。サブコピーに転用）

## 3. ページ構成（上から順に）

| # | セクション | 内容 |
|---|---|---|
| 1 | ファーストビュー | メインコピー＋サブコピー、画面写真（スマホとPC）、ボタン「PoCに申し込む」「1分でわかる動画を見る」 |
| 2 | 困りごと（問いかけ） | 「入退室の記録や利用時間の集計に、手間がかかっていませんか？」「カードを今だれが持っているか、すぐに分かりますか？」「会員への連絡が、電話・口頭・掲示だけになっていませんか？」「会議室予約やドリンク注文の受付が、受付の負担になっていませんか？」 |
| 3 | 運営者のためのシステム | 「働く人のため」ではなく「場をつくる人のため」。カード貸出、利用時間の管理、ドリンク注文、会員への連絡など、**運営ならではの業務**を扱えることを示す |
| 4 | 解決の全体像 | 来館 → 利用（予約・注文・連絡）→ 退館 → データ、を1枚の図で。会員・受付・本部が同じ仕組みでつながる |
| 5 | できること | 4つの柱（4章）。各機能に画面写真と2〜3行の説明 |
| 6 | 1日の運用イメージ | 9:00 QRで入室・カード貸出 → 10:00 会議室予約 → 12:00 ドリンク注文 → 15:00 受付からチャットで連絡 → 18:00 退室・カード自動返却。受付と本部の動きも並べる |
| 7 | 導入・運用がかんたん | インストール不要（ブラウザで動く）／受付手段はQRコードのほか、ICカード・番号入力・バーコードから選べる／**初期設定と会員データの登録は弊社が代行**／会員は登録用URLから自分で登録／今のシステムと併用できる（入退室データのCSV出力、Webhookでの自動通知） |
| 8 | 運営体制に合わせた権限 | マスター → 管理者 → 代表 → ユーザーのツリー図。「拠点ごと・入居企業ごとに管理を任せられる」。複数拠点の運営会社に効く訴求 |
| 9 | 想定される効果 | 立場別（利用者／受付／本部）のメリット。受付の記録作業の試算は「仮の前提での試算。実際の数値はPoCで計測」と必ず明記する |
| 10 | PoC参加企業の募集 | 期間・費用・募集社数（7章で決定）、弊社が行うこと（初期設定・スタッフ説明・期間中の改善）、PoCで確かめること（受付時間、カード確認の手間、会員の使いやすさ、電話・口頭の依頼件数）。結果は数字でまとめて報告 |
| 11 | 安心材料 | 実施済みのセキュリティ対策（HTTPS、パスワードの暗号化保存、権限による閲覧範囲の分離、チャットは当事者のみ閲覧）／解約時のデータの持ち出し（※扱いは7章で決定）／運営会社と代表の紹介 |
| 12 | よくある質問 | 5章 |
| 13 | ビジョン | 「スペース運営の Workspace OS を目指して」。今後の構想（AIによる受付チャット、混雑の見える化、複数拠点の管理）を「PoCで一緒に検証できます」と添える |
| 14 | 申し込み・お問い合わせ | フォーム（会社名・拠点数・会員数・連絡先）と会社概要 |

## 4. 「できること」で載せる内容

| 柱 | 打ち出し方 |
|---|---|
| ① 入退室・カード貸出 | QRコードで入退室を記録（※バーコード/ICカードも可。さりげない注記で添える）。入室時にカードを貸出し、退室時は自動で返却扱い。月の利用時間を自動でカウント（時間制のプランにも） |
| ② チャット | 受付コンシェルジュから会員へ1対1で連絡。未読がひと目で分かる |
| ③ ドリンク注文（ティーサーブのモバイルオーダー） | 会員はスマホから、口頭の依頼は受付が代理入力。どちらも1つの注文一覧で受け付ける |
| ④ 会議室予約 | 空き状況を見て、直感的に予約。間取り図から部屋を選ぶこともできる（間取り図はベータ版） |
| ＋ 会員登録 | 登録用のURL・QRを送るだけで、会員が自分で登録できる |

## 5. よくある質問の候補

- 専用の機器は必要ですか？（不要。ICカードで受付する場合は、受付PCにカードリーダーを接続）
- スマホを持っていない会員はどうしますか？（番号入力・ICカード・バーコードでも記録できる）
- 今使っている予約システムやカードと併用できますか？
- 会員の個人情報はどう扱われますか？
- 解約したら、データは返してもらえますか？
- PoCの期間と費用は？本導入の料金は？
- 複数の拠点をまとめて管理できますか？

## 6. 作るときのポイント・表現の注意

- **画面写真が一番の説得材料。** デモデータが入った今の画面を使う（撮影はオーナーが用意）。
- 読み手は「自分の拠点で回るか」を知りたいので、機能の数より **1日の運用の流れ** で見せる。
- 申し込みフォームの項目は絞る。詳しいことはヒアリングで聞く。
- **多言語対応**: 英語は一部のみ翻訳済み（2026-11-08時点）。「多言語対応」とは書かない。
- **権限の4段階**（マスター／管理者／ユーザー（代表）／ユーザー）: `backend/accounts/models.py` にロールがあることを 2026-11-24 に確認。画面の動作は、LPに載せる前に確認する（未確認）。
- **料金**: 本導入の料金は載せず、「PoCは◯円〜」または「お問い合わせ」にする（募集段階で価格を固めないため）。
- 他社名（オフィス向けの受付・会議室システム、家具・不動産系のスペース管理システム）は出さない。
