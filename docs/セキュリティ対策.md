# セキュリティ対策まとめ

作成日: 2026-10-13
対象バージョン: GitHubリポジトリ `main` ブランチ（コミット `2443723` 時点）

## 1. 目的

本アプリのセキュリティ面での安全性を説明・証明するために、現状の対策状況と
未対応事項を整理したもの。

## 2. 🚨 緊急対応が必要な既知の問題（本書作成時点で未対応）

### LINEトークンが公開GitHubリポジトリに平文で含まれている

- **内容**: `tools/ngrok_tunnel/notify_ngrok_url.py` に、LINE Messaging APIの
  チャンネルアクセストークンとユーザーIDがハードコードされている
- **深刻度**: 高。リポジトリ（`NaoyaHamazaki/project0827`）が**Public（公開）設定**
  のため、第三者が閲覧・取得可能な状態になっている
- **対応手順**（未実施）:
  1. LINE Developersコンソールで該当トークンを失効・再発行する（漏洩したものとして扱う）
  2. コードを環境変数経由の参照に変更し、リポジトリから平文の値を削除する
  3. 必要であればリポジトリ自体をPrivateに変更する（最も手早い根本対応）
- 上記3点とも**本書作成時点でまだ対応していない**。優先的に着手すること

## 3. 現状講じられている対策

| カテゴリ | 内容 |
| --- | --- |
| 認証 | JWT（`djangorestframework-simplejwt`）によるトークン認証。アクセストークン8時間・リフレッシュトークン7日間、ローテーション有効 |
| パスワード | Djangoの標準ハッシュ化保存（平文保存なし）。強度バリデーション4種（ユーザー情報との類似性・最低文字数・一般的すぎるパスワード・数字のみ禁止）を適用 |
| 認可（権限制御） | ロールベース（管理者／ユーザー）。会員管理・在室ログ・セキュリティカード管理・設定は管理者限定（`IsAdmin`パーミッションクラス） |
| チャット機能のアクセス制御 | 会話・メッセージ・リアクションの全APIが「自分が参加する会話」のみに限定され、第三者（管理者含む）には404を返す。自動テストで検証済み（`chat/tests.py`） |
| QRコードの不正利用対策 | `django.core.signing`による署名付きトークンを発行し、**5分で失効**させることで、画面キャプチャの使い回しによる不正入室を防止 |
| XSS対策 | チャットの太字表示はReact要素として描画し、HTML文字列の挿入（`dangerouslySetInnerHTML`等）は一切使用していない |
| SQLインジェクション対策 | 生SQLを使用せず、全てのDB操作をDjango ORM経由で実施（確認済み） |
| 本番起動時の安全装置 | `DEBUG=False`で起動する際、開発用の既定`SECRET_KEY`のままだと**起動自体を拒否**する仕組みを実装済み（`backend/config/settings.py`） |
| 機密情報の環境変数管理 | `DJANGO_SECRET_KEY`・`DATABASE_URL`・`DEMO_GATE_PASSWORD`等は環境変数で管理し、コードに平文で含めていない（2章のLINEトークンを除く） |
| デモ環境への簡易アクセス制限 | 共通パスワードによる「デモ公開用ゲート」をログイン画面の手前に設置（一時的対応として実装、環境変数未設定時は自動的に無効） |
| デバッグ機能での情報保護 | 設定ページの「テーブル確認（開発用）」機能は、パスワードハッシュやWebhookシークレットなどの値を自動的に`（非表示）`にマスクする |
| セキュリティカード貸出の整合性 | 貸出中カードの二重貸出を防止、退室時は会員が借りているカードを自動で返却扱いにする業務ロジック |

## 4. 追加で実施を推奨する対策（未対応）

### 優先度：高

- **ログイン試行のレート制限（未対応）**: ログインAPI（`/api/auth/login/`）、
  デモゲートのパスワード確認API（`/api/auth/gate/verify/`）のいずれにも
  回数制限が設定されておらず、総当たり攻撃が可能な状態。DRFの`throttle`機能で
  比較的簡単に追加できる
- **セキュリティヘッダーの追加（未対応）**: `X-Frame-Options`、
  `X-Content-Type-Options`、HSTS（`SECURE_HSTS_SECONDS`）等、Django標準の
  セキュリティミドルウェア設定が未調整

### 優先度：中

- **Django管理画面（`/admin/`）の扱い（未検討）**: `/admin/`は現状誰でも
  URLにアクセスしてログイン試行ができる状態。実運用で使わないなら無効化、
  使うなら強固なパスワード設定とアクセス制限を推奨
- **依存パッケージの脆弱性チェック（未実施）**: `pip list --outdated` /
  `npm audit` 等で既知の脆弱性がないか未確認
- **Webhook機能のSSRF対策（未対応）**: 管理者が任意のURLをWebhook通知先として
  登録できる仕様のため、内部ネットワーク宛てのURL（例: クラウド基盤のメタデータ
  エンドポイント等）を弾く等の制限が入っていない。管理者限定機能のためリスクは
  相対的に低いが、デモ公開を前提とするなら対応しておくと安心

### 優先度：低（運用が固まってから）

- 管理操作（会員情報編集・設定変更等）の監査ログ（誰がいつ何を変更したかの記録）
- Railway上のPostgreSQLの自動バックアップ設定の確認

## 5. まとめ

認証・認可・XSS/SQLインジェクション対策・QRコードの不正利用対策など、
基本的なセキュリティ対策は実装済みと言える状態。一方で、**LINEトークンの
リポジトリ公開という実害のある問題が1件未対応**で残っており、最優先で
対応が必要。そのほか、レート制限の欠如など、本格的な外部公開前に
埋めておきたい項目がいくつか残っている。
