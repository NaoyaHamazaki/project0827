# 引継ぎ情報：project0827戦略（コワーキング受付・カード貸出管理）

作成日：2026-09-04

## 全体像

project0827は、ユーザー（GLORIS代表・浜崎氏）が契約しているコワーキングスペースの「ニーズがありそうだ」という予想から個人開発したMVP。当初は「受付・入退室管理システム」として、会員カードのスキャンで入室/退室をトグルする設計で作られた。

FELDNA（学校向け業務システム）が本業の柱で、project0827は資金繰りが厳しい中での**副次的な検証案件**という位置づけ。「まだ買うと言っていない相手のための作り込みは避け、まず1回の会話で決着をつける」という方針を過去に確認済み。

## 直近の展開（重要）

ユーザーが実際にそのコワーキングスペースを訪問し、受付の実態をさらっと聞いたところ、**当初の想定と異なる実業務が判明した**。

> 受付でカードを受け取ったらセキュリティカードらしきものを渡し、カードと渡したセキュリティカードの番号を紙に手書きして記録している

これは「入退室管理」ではなく、**「セキュリティカードの貸出・返却管理」**が本質。会員証とセキュリティカードのペアを紙に記録しているのは、貸したカードを誰が持っているか追跡する必要があるため。ここでプロジェクトの方向性が明確になった。

### この発見の意味
- 現状のデータモデル（会員カード1枚をスキャンして入退室をトグル）には「貸与したカード番号」という概念がなく、実業務とズレている
- 逆に言えば、貸出カード番号の欄と返却状態を足すだけで、今の手書き作業がそのまま置き換わる
- 受付で答えてくれた人はおそらく決裁者ではない（動機は「面倒」）。お金を出す運営者の動機は「損失」であり、次に聞くべきはそちら側の質問

### 運営者に次に確認すべき項目（未実施）
- カードが返却されないことはあるか。あった場合どう対応しているか（紛失コスト・セキュリティ判断の根拠になる）
- 紙の記録を後で見返すことがあるか（監査・トラブル対応・利用実績集計）
- 1日あたりの貸出件数（手間の総量を数値化）
- 受付は常時有人か（無人時間帯があれば別の価値提案になる）

### 汎用化の仮説（未検証・保留）
「入館証を貸し、番号を紙で紐付け、返却を確認する」業務は、貸会議室・ビルの来訪者受付・ジムのロッカーキーなど、コワーキング以外にも広く存在する可能性がある。市場を「コワーキング向け」ではなく「貸与品の受付管理」と捉え直せるかもしれないが、現時点では仮説止まり。決めつけず保留。

## 現状のコード構造（確認済み）

- 構成：Django（`backend/`）＋ React（`frontend/`）
- 画面：①スキャン受付 ②会員管理 ③在室・ログ管理（2ロール：Operator/Admin）
- 主要モデル：
  - `members.Member`：id, name, company_name, **card_identifier**（会員カードのID、ユニーク）, status, plan
  - `access.AccessLog`：member（FK）, type（check_in/check_out）, method（card/pin/qr/fingerprint/phone/manual）, scanned_by, created_at
  - → **現状、貸与カードという概念が一切存在しない**
- ICカードリーダー（RC-S380 / PaSoRi）連携ツールが `tools/rcs380_bridge/` にあるが、**これ以上の作り込みは保留中**（相手が「今のカードをそのまま読ませたい」と言うまで着手しない方針）
- gitリポジトリは未初期化（HANDOFF.md記載時点）

## 直前に整理した改修要件（未着手・コード化はこれから）

### データモデルの追加
**新規：`SecurityCard`（貸与カード台帳）**
- card_number（紙に手書きしている番号に対応）
- status：在庫 / 貸出中 / 紛失 / 廃止

**新規：`CardLoan`（貸出記録）**
- member（FK）, security_card（FK）
- issued_at, issued_by（貸出日時・担当者）
- returned_at, returned_by（返却日時・担当者。未返却はnull）

既存`AccessLog`との連動：CHECK_IN発生時に`CardLoan`を1件作成、CHECK_OUT発生時に対応する`CardLoan`のreturned_atを埋める。入退室ログはそのまま活かし、その上に貸出状態を重ねる設計。

### 画面の変更（4画面構成へ）
1. **スキャン受付**（既存）：会員カードスキャン後、貸すセキュリティカードを選択/スキャン。退室時は返却カードを選択/スキャンし、貸出時と一致するか自動照合
2. **会員管理**（既存）：変更小。必要なら現在の貸出状況を会員詳細に表示
3. **在室・ログ管理**（既存）：列追加（貸したカード番号、返却済み/未返却）、「未返却のみ」フィルタを追加
4. **セキュリティカード管理**（新規画面）：カード台帳一覧（在庫/貸出中/紛失/廃止）と貸出中カードの現在の保持者。カードの追加・廃止

### 運営者への「発展性」提案の軸
紙の手書き管理は「記録」はできても「今何が起きているか」の把握ができない、という一点を突く。
- リアルタイムの貸出状況（今何枚外に出ていて誰が持っているか）
- 未返却アラート（営業終了後も返却されていないカードを自動検知）
- 紛失・損傷履歴の蓄積（再発行コストの根拠データ）
- 複数拠点への展開（カード台帳とログの構造を整えておけば、店舗が増えても同じ仕組みで一元管理できる）→ 単独店舗の話を「仕組みの提案」に引き上げる一言
